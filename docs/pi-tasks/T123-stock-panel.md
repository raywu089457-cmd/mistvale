# T123 倉庫面板：分組＋用途／來源

Status: done
Type: ui
Accept: `node tools/checks/stock-panel.mjs && npm run verify:quick`

## Goal

倉庫（背包）原本是一格一格的圖示＋名稱＋數字，完全沒有「這東西能幹嘛、去哪裡拿」的資訊。
玩家看到『獸皮 12』不知道能做護甲，看到『鐵礦 0』也不知道該去打誰。這輪：

1. 分成三組：**材料**（6 種）、**生活物資**（4 種）、**裝備**（2 種），每組標題右邊寫「持有 N／M 種」。
2. 每項寫：
   - 名稱、數量、單價（`單價 2 金`，材料才有實際交易價）
   - **用途**：從 `PRODUCTS`／`RECIPES` 的 `cost` 反推（木材→精鐵武器；獸皮→舒適床鋪、皮革護甲；
     小麥粉→香烤麵包……），沒人用到的寫「交易或村莊委託」。
   - **來源**：從 `ENEMIES[*].drops` 反推會掉這項的魔物名字；沒有魔物掉落的再分組給 fallback
     （材料→交易所收購、物資→自己的設施製作、裝備→鐵匠鋪製作）。
3. 上方摘要條：`持有 9／12 種 · 共 67 件`。
4. **數量 0 的項目不再整個消失**，改成淡化（opacity .55）——倉庫同時是一份「還有什麼可以收集」的清單。

## Decisions

- **用途／來源都用資料推導，不維護第二份文案**：改配方或掉落表時說明會自動跟著變；
  檢查器也是驗「推導結果」而不是驗某段寫死的字串（實測就抓到我一開始把木材寫成也能做床鋪，
  其實床鋪只吃獸皮＋亞麻布）。
- **空品項顯示但淡化**：直接藏起來會讓「有哪些資源存在」變成只能靠記憶；
  但也不能讓它跟有貨的一樣醒目，所以用 opacity 而不是移除。
- **fallback 分組說法**：材料→「交易所收購」、物資→「在自己的設施製作」、裝備→「鐵匠鋪製作」，
  三種來源語意不同，不能共用一句。
- **不改 `stock()` 的取值順序**（`state[id] ?? state.stocks?.[id] ?? state.gearStock?.[id]`）：
  這是既有資料佈局，UI 只讀不寫。

## Notes

- 用途／來源文字會換行（不是 ellipsis）——名稱較長的組合（亞麻布→舒適床鋪、亞麻繃帶、皮革護甲）
  用省略號會剛好切掉最想看的第三項。
- 檢查器的期望數量是**從 state 直接算**（同樣的取值順序），不是寫死：繃帶有初始庫存 30，
  寫死 0 會誤判。
- 檢查器也會驗 `source.length`、`use` 前綴、空品項的 `.empty` 與 opacity、摘要的種類／件數、
  以及手機單欄（同組左緣只有一個 x）。
- 這輪只動 UI 顯示，沒有改倉庫的資料結構或任何消耗邏輯。
