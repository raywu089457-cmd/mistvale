# 實驗 5：UI 樣式 token 化（派工 vs 不派工 對照實驗）＋派工系統改進清單

日期 2026-11-03。方法沿用 `docs/DISPATCH-PLAYBOOK.md`，成本算法同 `docs/pi-tasks/COST-LOG.md`（weighted = 未快取×1、快取寫×1.25、快取讀×0.1、輸出×5）。

---

## 一、為什麼選這個任務

量了目前的 UI 債（2026-11-03，`src/pixel-style.css` 1,191 行）：

| 指標 | 數量 |
|---|---|
| 不同的 hex 色碼 | **730**（JS 另有 8 個） |
| `:root` 的自訂屬性 | 16 個 |
| `font-size: Npx` 宣告 | **377**（同一字級在 base / 手機 / 桌機 / 修補區塊各寫一次，靠先後順序決定） |
| `pixel-ui.js` 內聯 `style=` | 13 處 |

TMW 統整（`docs/TMW-STUDY-SYNTHESIS.md` 第三節）早已把這列為「做，分批」，第 1 批（T20）只做了一小部分。這個任務適合當實驗，原因：

1. **夠大**：730 色碼＋377 字級，Claude 自己做要讀完整個 CSS 好幾遍，預估 >300k weighted。
2. **可切成兩半**：CSS 依區塊切成 A、B 兩組，難度相近，一組 Claude 自己做、一組派 pi，同一個任務直接比。
3. **對錯能用指令驗**：目標是「畫面一個像素都不變」，可以用 computed-style 快照比對，不靠人眼。
4. **三種難度都有**：純機械（色碼）、結構性（字級去重，會碰 cascade 順序）、要人眼（圖示整數倍）。剛好測手冊裡三條預測。

### 第 0 階段實測後的修正（2026-11-03）
- **730 個色碼幾乎每個都不一樣**（前半 464 次使用裡有 442 種）。要壓到 50 個 token 就得把 ΔE≈10 的顏色合併，肉眼看得出來。改成：**ΔE ≤ 2（肉眼分不出，JND≈2.3）且用 ≥3 次的才合併** → **66 個 token、取代 363 次使用**。其餘色碼留著，之後要人眼審的批次再處理。
- 驗收：`style-snapshot.mjs --tol-de 2`（顏色移動 ≤ ΔE 2 不算差異）。已實測：沒改時 0 差異（7,614 個元素，無雜訊）；全部 `#e9d6a8` 改掉抓到 114 筆；只偏 ΔE≈1 時嚴格模式 114 筆、容差模式 0 筆。
- 切點用兩個註解 `/* @split color */`、`/* @split font */`（不影響畫面），兩軌各自 50/50：色彩 182 / 181 次、字級 196 / 180 個。
- 順手發現：有些規則永遠被後面的蓋掉（第一個 `#e9d6a8` 改了畫面沒變），CSS 裡有死宣告。
- **K1 其實寫腳本就能做完**（表已經有了，只剩逐一替換）。兩組都不禁止寫腳本：這正好測手冊的「短腳本能解決就自己做」。真正考驗派工的是 K2（要懂 cascade）。

## 二、任務內容（三條軌道）

| 軌道 | 內容 | 手冊預測 | 驗收 |
|---|---|---|---|
| **K1 色彩 token** | 730 個 hex → 約 40–60 個語意 token（`--wood-dark`、`--parchment`、`--text-muted`…），值完全不變 | 派工大勝（像實驗 3） | 樣式快照 0 差異 ＋ `:root` 以外的 hex 數下降到目標 |
| **K2 字級去重** | 377 個 px 字級 → 字級 token（`--fs-xs`…`--fs-xl`）＋把同一選擇器在多個 @media 的重複宣告合併 | 派工小勝或打平（需要懂 cascade） | 樣式快照 0 差異 ＋ 重複宣告數下降 |
| **K3 圖示整數倍** | 32×32 原圖被縮到 17/19/21/22/27/29px 的地方改成 16/24/32 | 不派較好（要看截圖） | layout checker 0 FIX ＋ 人看前後截圖 |

K3 會動到像素，排最後，也是唯一要使用者看截圖的一軌。

## 三、實驗設計：交叉對照（crossover）

只比「同一半」會被「這半比較難」干擾，所以兩條機械軌交換：

| | CSS 前半（HUD、頂欄、側欄、地圖） | CSS 後半（彈窗、設定、手機操控、PixelLab 皮膚） |
|---|---|---|
| **K1 色彩** | Claude 直接做（S1） | 派 pi（S2） |
| **K2 字級** | 派 pi（S3） | Claude 直接做（S4） |
| **K3 圖示** | 偵察卡 → Claude 決定 → 實作卡（S5） | Claude 直接做（S6） |

切點：用第 0 階段的 `css-debt.mjs` 找 hex 數最接近 50/50 的區塊註解（大約在 `/* ===== 2026-10-28 PixelLab UI 零件` 前後），兩半 hex 數相差 ≤10%。

### 公平性規則
- **每個 S 都是新 session**（或 /clear），模型 Sonnet 5.5 medium，同一份 CLAUDE.md。上下文不共用，第二個做的不會因為記得前一個而便宜。
- 第 0 階段的共用成本（色盤對照表、驗收工具）單獨記帳，不算進任何一組。兩組拿到的是同一份對照表，都只是「套用」。
- Claude 直接做的那組，**一樣要達到同一個驗收**（快照 0 差異），不能因為「自己做」就少驗一次。
- 記 **返工**：驗收過了之後、或下一軌開始前發現要回頭修的 token，算回原來那組。
- 每組結束時記：Claude weighted、Claude 呼叫次數、pi USD、牆鐘時間、驗收次數、返工次數、最終指標（剩下幾個 hex／幾個重複字級）。

## 六、現在的派工系統還能改哪裡

依據：`cost-log.csv` 31 筆、`tools/pi-dispatch.mjs`、COST-LOG 實驗 1–4。依「省多少 Claude token」排序。

### 1. Claude 端成本沒有自動記帳（最該先做）
`cost-log.csv` 只記 pi 的美元，Claude 那邊每次都要手動抓時間窗跑 `claude-usage.mjs`；而且 COST-LOG 寫的逐字稿路徑還是舊的 `C--Users-ray-Desktop-Claude-code`，現在是 `C--Users-ray-Documents-Codex-2026-09-29-new-chat-work-mistvale`。
**改法**：`pi-dispatch.mjs` 開始和結束時印 ISO 時間並寫進 CSV；新增 `tools/session-cost.mjs`，自動找本專案最新的 `.jsonl`，一次算整個 session（或從 session 起點到現在）。實驗 5 的六組數字就靠它，不然光是記帳就要多花 Claude 呼叫。

### 2. 「改到的檔案是否在範圍內」還要 Claude 自己比
手冊 4.2 要 Claude 拿「改到的檔案」對卡片的「Files you may change」。這是純字串比對。
**改法**：派工腳本解析卡片的 Files 清單，超出範圍的檔案直接標 `SCOPE!` 並讓結果不算 ok。Claude 少讀一段、也少漏看。

### 3. pi 的時間和花費在變貴，但看不出原因
| 卡片區間 | 平均牆鐘 | 平均 pi 花費 |
|---|---|---|
| T07–T10（11/01） | 約 5–16 分 | 約 US$0.03 |
| T33–T41（11/02） | **約 35 分** | **約 US$0.10** |

CSV 只有總額，看不出是 pi 在探索（讀太多）、驗收太慢、還是生圖等待。
**改法**：CSV 加 `pi_calls, pi_cache_read, accept_sec` 三欄（`sessionCost` 已經在讀 session 檔，順手數就有）。之後才知道該改卡片還是改驗收。

### 4. 自動重派從沒被觸發過
31 筆全是 `attempts=1`。T36 是 BLOCKED（不重派，正確），其他都一次過或沒有驗收。重派機制還沒被證明有用，也沒被證明安全。
**改法**：實驗 5 的 K2 是第一個可能觸發它的場合，記下重派那次的成本；若重派常常只是重複同樣錯誤，改成「重派前先附 accept log 的差異摘要（前 20 行），而不是最後 5 行」。

### 5. 驗收腳本散落在 `output/`，不能重用
T33/T34/T36/T41 用 `output/layer-demo/check.mjs`，T39/T40 用 `output/sr-demo/…`。`output/` 是產出區，容易被清掉，下一個任務也找不到。T30–T32 甚至沒有 `Accept:`（CSV 記 `n/a`）。
**改法**：驗收腳本一律放 `tools/checks/` 或 `pipeline/scripts/ui-audit/`；`pi-card.mjs` 在沒有 `--accept` 時拒絕建卡（偵察卡除外），強迫每張卡都有可信的驗收。

### 6. 一次只能派一條，長卡互相排隊
同時建置會互刪 `outputs/media`，所以只能串行。T39→T41→T40 三張就排了 2 小時以上。
**改法**：`--parallel` 改成每張卡開一個 git worktree（`git worktree add output/wt/Txx`），在各自的資料夾建置，結束後把 diff 套回主目錄。這不省 Claude token，但省牆鐘，讓「一批一個 session」更可行。

### 7. 記憶和手冊互相矛盾
記憶 `dispatch-everything` 寫「每個任務都派」，手冊第 1 節寫「要先讀程式才能寫卡、或一個短腳本就能解決時，自己做」；實驗 1 就是派了反而更貴。Claude 每次都要猶豫一下。
**改法**：把記憶改成「預設派工，但遵守 DISPATCH-PLAYBOOK 第 1 節的例外」，跟 CLAUDE.md 一致。（這條要你同意才改。）

### 8. 每次 Claude 呼叫的固定成本
CLAUDE.md＋記憶＋系統提示每次都重讀，手冊實測 10/31 session 每次呼叫約 84k。省呼叫次數比省字更有效：
- 派工結果目前每張卡印 1200 字元，多卡時最後還有總表。批量大時改成**預設只印總表＋失敗卡的細節**，成功卡細節留在檔案。
- 一個批次結束要求 pi 在結果檔第 2 行給「建議下一步」一行字，Claude 不必再讀檔案判斷。

### 9. 品質沒有被記帳
目前只記「pi 說 DONE＋驗收過」，沒記「之後 Claude 或你有沒有回頭修」。實驗 2 的 `BLOCK_PLAN` 漏項、實驗 4 的裁切瑕疵都只寫在文字裡。
**改法**：新增 `node tools/pi-dispatch.mjs --review T35 ok|fixed "原因"`，在 CSV 補一欄 `rework`。實驗 5 的返工數就用它記。

### 10. 實驗 5 K1 新發現（2026-11-03）
- **等待讓快取過期**：派工組每 10 分鐘醒一次，每次快取讀為 0、整段 ~67k 重寫，四次就吃掉 ~335k(總 434k)。直接做組只要 99k。改法：派工一律背景執行，只在完成通知時醒一次；子代理（5 分鐘快取）不要做長派工。
- **pi 每張卡都在跑完整 verify**：共用提示詞的回報格式要求 `verify: <verify-summary 第一行>`，pi 因此每次跑 12 分鐘以上的按鈕爬蟲（T43 37 分鐘大多花在這）。改法：卡片有 `Accept:` 時，回報格式改成 `accept: <結果>`，提示詞明說「不要跑 npm run verify，除非卡片要求」。
- **範圍檢查會誤報**：派工期間 Claude 自己改的檔案也算在 pi 頭上（T42 誤報 `scope OUT`）。改法：派工期間主對話不要改檔，或快照時記下 mtime，只算 pi 那段時間被 pi 的工作目錄寫入的檔。

### 12. 派工 v2:只省 Claude(pi 不計成本,2026-11-03)
實測 Claude 成本由四件事決定，依大小:
1. **每個新上下文的固定成本 ≈ 7.9 萬 token**(系統提示、工具定義、技能清單;CLAUDE.md+記憶只占 ~2k)。冷啟動一次 ≈ 10 萬 weighted。→ 子代理、新 session 都要付這筆;**一批工作只開一個上下文，不用子代理**。
2. **呼叫次數**:之後每次呼叫重讀整段(快取讀×0.1),長對話一次 2–3 萬。→ 一批 = 寫目標 1 次 + 派工 1 次 + 讀總表 1 次。
3. **等待時快取過期**:等超過快取壽命就整段重寫。→ 背景派工、完成才醒一次。
4. **讀程式、讀 log、寫細卡(輸出×5)**。→ 全部改給 pi。

v2 分工(T45 實作):
| 原本 Claude 做 | v2 誰做 | 品質怎麼守 |
|---|---|---|
| 讀程式寫 Steps / Files | pi 的 PLAN 階段 | 範圍檢查改用 plan 的 Files |
| 想驗收指令 | `Accept: auto` 時 pi 提出(只能用現有檢查或自己寫進 `tools/checks/`) | PRECHECK:新檢查在未改動時就通過 → 退回重寫(證明不了東西) |
| 看 diff 判斷有沒有做歪 | 另一個 pi 的 REVIEW 階段(批評者提示詞) | 有 high 問題就自動重做，最多 3 次 |
| 讀結果摘要 | 預設只印一行;沒過的卡才印細節 | `accept PASS` + `scope ok` + `review OK` 三關都過才算過 |

Claude 仍然要做的(不能省、也不該省):分類任務(C 級邏輯照舊派 `game-logic-opus`)、寫一段目標、看需要人眼的截圖(pi 指出一張就好)、決定要不要 commit。

**環境(要你決定)**:固定成本的大頭是全域技能/外掛清單(上百個網頁設計技能、瀏覽器與電腦操作 MCP)。在這個專案停用用不到的，每次冷啟動和每次呼叫都會變便宜。這是設定變更，要你點頭才改。
